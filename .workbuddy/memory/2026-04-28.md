## taskId 后缀（`EV-0003-cWQMJx` 里的 `cWQMJx`）的必要性辩证

### 触发
用户在会话里看到多次出现的 `EV-0003-cWQMJx`、`EV-0003-jPHHCU` 这种带 6 位随机后缀的 taskId，疑惑后缀到底是干啥的、是否多余。

### 结论：必要，不能删

### 三大现实理由（按重要性）
1. **reconcile 身份锚**（硬依赖）：`codeRegistry.ts::buildTaskIdToQueryIdMap` 同时建 `byTaskId` 和 `bySuffix` 双索引。`queryCode`（EV-0003）会被启动期 reconcile 归一化重命名，但 suffix 永不变，是 inbox/outbox/query 三方唯一稳定的跨文件引用键。
2. **并发防撞**：seed / migrate 脚本批量跑时，同秒同 code 生成有概率撞车，suffix（nano6 = 6 位字母数字，≈57 bit 熵）是"几乎不可能碰撞"的唯一保证。
3. **URL capability 弱防护**：taskId 是所有 `:taskId` 端点的 URL slug，6 位随机后缀让 URL 自带 token 性质 —— 不知道完整 taskId 就访问不到对应文件。

### 代价（诚实列一列）
- 日志 / URL / filename 可读性下降（7 字符视觉噪音）。
- 用户在 UI 上看到会产生"这是什么"的认知成本（本次对话就是例证）。
- **但这些都是展示层问题，不是身份层问题。**

### 后续可做（非本次范围）
- 日志/UI 里给 taskId 加 tooltip 或分段展示，明示"EV-0003 = 业务号 / -cWQMJx = 不可变锚"，降低认知门槛。
- 如果要进一步优化，可以在人可读场景同时展示 `queryCode` + `taskId` 两段。

### 涉及文件（只读，本次无代码改动）
- `src/lib/contract.ts:572-587`（`nano6` + `makeTaskId`）
- `vite-plugins/codeRegistry.ts:351-395`（`parsePrefixCode` + `buildTaskIdToQueryIdMap` + `extractSuffix`）
- `vite-plugins/codeRegistry.ts:408-426`（`renamePrefix`，reconcile 重命名时保留 suffix 的关键逻辑）
- `vite-plugins/bus/helpers.ts:97-101`（`parseQueryCode` 从 taskId 反解 queryCode）

### 沉淀
已更新 `MEMORY.md` → 新增"taskId 双段结构"条目，写清楚设计出处和不可删原因，避免后续再次踩同款认知疑惑。

## 胶囊"未参评"徽标升级为"待评测"：替换正文后也能提醒

### 触发
用户观察到：先前给 ReportPage cohort 胶囊加的"未参评"徽标只能抓到「新增产品从未召唤」这一种场景；**走「编辑对比源 → 替换正文」后没再召唤评测**的场景完全不提醒（因为这份 submission.id 早就在 inbox 里，`inboxHistoryMap.has()` 仍为 true）。用户直觉判断："其实应该对比 最新评测时间 vs 最新对比源变动时间（只看正文变动，不算元数据改动）"。

### 辩证结论
用户直觉正确，且比旧实现语义更干净。旧判据是"submission 是否进过 inbox"（布尔），新判据是"最新一次正文变动 vs 最新一次评测"（时间比较）。新模型天然契合契约：contract 保证改元数据走 `updateSubmission` 只动 localStorage 不追加 `reportVersions`；只有替换正文走 PATCH inbox 才会 push 一条新 version，所以用 `reportVersions[last].submittedAt` 做"正文变动锚"干净无歧义。

### 实现（`src/pages/ReportPage.tsx`，~70 行增量）
- 新增派生 `latestEvalMtime = max(outboxTasks.latestMtime)` 和 `pendingSubIds: Set<string>`，对每个 submission 取 `inbox.reportVersions[last].submittedAt`（回退链：`submittedAt → replacedAt → producedAt → sub.createdAt`），与 `latestEvalMtime` 比大小。
- Hero 胶囊 `showPendingBadge` 从 `!hasInbox` 换成 `pendingSubIds.has(sub.id)`；徽标文案 `未参评 → 待评测`；tooltip 区分两种场景（全新未召唤 / 正文已更新待重评）。
- 图例出现条件从 `cohort.some(没 inbox)` 换成 `pendingSubIds.size > 0`；文案改为"灰点 = 对比源在最新评测之后有更新，建议重跑评测"。
- **「召唤评测」按钮右上角加小红 badge**：`pendingSubIds.size > 0` 时出现数字徽章（`bg-clay text-white` + `ring-2 ring-white`，18px 圆），tooltip 提示"有 N 个对比源在最新评测之后发生了变动，建议重跑一次评测"。
- **零改动**：store / types / contract / lint / inbox/outbox 写入链路完全不动，纯前端派生。

### 踩坑：React Hooks 顺序
首次落地把两个 `useMemo` 放在了 `if (!q) return` **之后**，触发 `react-hooks/rules-of-hooks` 报错。必须移到所有 early return 之前。已在代码注释里显式标注。

## 按钮 badge 二次迭代：数字 → 脉冲小圆点

### 触发
用户反馈："其实没必要给数字，只需要一个示意，提醒说'需要再跑一次新的评测'即可。"——数字是过载信息，用户只需要"有/无"这个信号量。

### 设计选型辩证
列了 4 个方向：① 静态小圆点（太静）；② **脉冲小圆点（animate-ping 光晕）**；③ 小闪电/刷新 icon（和 🤖 emoji 语义打架）；④ 按钮本体变色（破坏 hover 状态）。

最终选 ②。理由：
- **零信息量但有视觉权重**：不说"几个"，只说"有"，契合用户意图。
- **脉冲呼吸**是 Linear / Notion / GitHub 等主流产品统一的"柔性提醒"语言，大众心智成本低。
- 和按钮本体 🤖 emoji 互不抢位。
- Tailwind `animate-ping` 周期 1s，足够低调不烦人。

### 实现（`src/pages/ReportPage.tsx`）
双层 span 结构（Tailwind 官方通知点标准模式）：
- **外层 `animate-ping`**：同色半透明光晕，持续脉冲，制造呼吸感。
- **内层实心圆点**：`7px × 7px` + `bg-clay` + `ring-2 ring-white` 外描边，在深色按钮背景上清晰可见。
- 位置 `-top-0.5 -right-0.5`，比之前的 18px 数字徽章更贴合按钮边缘。
- 语义通过 `aria-label` + 按钮本体 tooltip 表达"待评测数量 + 建议重跑"。

## v3.4 taskId 扁平化：`taskId === queryCode`

### 触发
上一节给按钮加"待评测脉冲点"时，顺带发现一个更深的工程债：同一 query 被多次「召唤评测」会在 outbox 下生成一堆碎片化目录 `EV-0002-abc/`、`EV-0002-xyz/`...，前端 `pickLatestTaskByQueryCode` 只展示最新那个，**其余历史版本全被"埋了"**。根因是 `makeTaskId()` 每次都拼新 nano6 后缀。

### 辩证：suffix 身份锚可以让位
- 日志里记了三个保留 suffix 的理由（reconcile 身份锚 / 并发防撞 / URL 弱防护）
- 重新审视：reconcile 主键可以用 payload 里冗余的 `queryId`（UUID）承担；并发防撞场景只在 seed/migrate 批量跑，那里本来就有自己的去重；URL 弱防护是"安全感"而非真安全
- 结论：suffix 的弱防护价值 < 目录碎片化的真成本。扁平化

### 实现
- `src/lib/contract.ts::makeTaskId` → `return queryCode`（删 nano6）
- `contractVersion` 联合类型加 `"3.4"`；`DEFAULT_RUBRIC_NAMES` 同步加映射
- `vite-plugins/bus/handlers/inbox.ts::handlePostInbox`：文件已存在时**不再 409**，按 `candidateId` 合并 candidates（新的追加；已有的保留磁盘权威副本，含 reportVersions / activeReportVersion / productVersion / authorNote；顶层 query 元信息以新提交为准）
- `vite-plugins/bus/helpers.ts::parseQueryCode` 正则 `^([A-Z]+-\d+)(?:-|$)` 兼容两种形态
- `vite-plugins/codeRegistry.ts::parsePrefixCode / renamePrefix` 同时认扁平化 `EV-XXXX` 和历史 `EV-XXXX-suffix[.json]`
- `scripts/migrate-consolidate-outbox.mjs`：一次性按 mtime 合并历史目录
  - 迁移产出：6 outbox 扁平化目录 + 6 inbox 扁平化文件；旧 suffix 目录清除
  - payload 里 `taskId` 字段同步重写为扁平化形式
- `scripts/lint-outbox.mjs` 允许 `contractVersion="3.4"`

### 边界隔离再确认
vite-plugins 下的 helpers 继续遵守"禁 import src/"的硬约束，helpers.ts 里加的正则 + `inbox.ts` 里的合并逻辑全部落在 plugin 层，没有跨边界拉 src 模块。

## taskId 工作复盘（2026-04-28 全量完成后）

### 心得

**一、"三个理由守住"不等于"三个理由都成立"。**
早上写 daily 时我列了 suffix 的三大必要性（reconcile 锚 / 并发防撞 / URL 弱防护），当时推论是"必要，不能删"。但下午真正评估"目录碎片化把历史版本埋掉"这个代价之后才发现：
- reconcile 锚：queryId（UUID）同样冗余在 payload 里，本来就是 reconcile 的真主键，suffix 是第二道保险
- 并发防撞：只在 seed/migrate 批量场景下发生，那里的生成器完全可以自己加去重；实际用户点"召唤评测"是手动节奏，不存在并发
- URL 弱防护：本地私有数据 + GitHub Pages 静态产物，攻击面几乎为零；"不知道完整 taskId"根本不是安全边界

三个理由不是假的，但**权重全部是"锦上添花"**，加一起也压不过"目录碎片化导致历史被埋"这个真实损伤。早上那篇 daily 有点自我说服的味道，下午推翻它是对的。

**二、契约改动的"真成本"在迁移，不在代码。**
代码改动就五六处（makeTaskId / parseQueryCode / codeRegistry / inbox POST 合并 / contractVersion 联合类型）。真正耗时间的是：
- 写 `migrate-consolidate-outbox.mjs` 时需要想清楚"两个 suffix 目录下 v1 撞了怎么办" → 按 mtime 升序排，重新分配 v1..vN
- 迁移时 payload 里 `taskId` 字段也要就地重写，否则 lint 会挂
- inbox POST 的合并语义要把"磁盘权威 vs 新提交"想清楚：reportVersions / activeReportVersion / productVersion / authorNote 走磁盘权威（保 PATCH 历史不被轧平），query 顶层元信息走新提交（允许用户改 title/description）

这些细节一个不写就翻车。真要复用经验：**结构性重构，代码只是 20%，数据迁移 + 语义兼容层是 80%。**

**三、"历史兼容"不等于"生成新旧两种"。**
v3.4 的姿势是：旧数据继续按 v1.0~v3.3 渲染（读兼容），新数据只生成扁平化形态（写单一形态）。contractVersion 联合类型里保留 "3.3" 也允许，是给"3.3 时代写完但还没来得及 bake"的产物留的缓冲，不是让我继续生成 3.3。这个区分很关键——写兼容才是债，读兼容是资产。
